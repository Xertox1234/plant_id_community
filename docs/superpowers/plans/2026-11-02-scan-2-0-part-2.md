# Scan 2.0 Part 2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the app diagnosis-first. The scan becomes a background,
multi-photo server job with per-user daily allowances. Its photos are stored
privately, and a push notification opens a result that shows the diagnosis.

**Architecture:**

- A new `ScanJob` model and its role-tagged `ScanJobImage` photos live in
  `apps/plant_identification`. The photos use a private storage backend. A
  Celery task runs the providers through a new
  `CombinedPlantIdentificationService.scan()`, classifies the outcome (done,
  degraded or failed), charges the allowance and pushes FCM.
- On the phone, a keep-alive Riverpod `ScanJobTracker` uploads the photos,
  polls the job and drives an app-wide pill overlay. Push routing opens a new
  `/scans/:id` result route.
- The work ships as **three PRs**:
  - Phase A: wording and home, mobile only, independent.
  - Phase B: backend.
  - Phase C: mobile job flow, which needs B deployed.

**Tech Stack:** Django 5 + DRF + Celery + django-storages 1.14.6 (S3/R2) +
firebase-admin FCM; Flutter + Riverpod 3 code-gen (`@riverpod`) + go_router +
Dio + flutter_secure_storage.

**Spec:** `docs/superpowers/specs/2026-11-02-scan-2-0-part-2-design.md` (parent:
`docs/superpowers/specs/2026-10-24-scan-2-0-design.md`).

## Global Constraints

- Free: **1 diagnosis/day**; premium: **3 diagnoses/day** (owner). Identify-only
  allowance: free **5**/day, premium **20**/day. All four values come from
  env-backed settings, along with the Plant.id daily cap (default **3**) and
  monthly cap (default **100**).
- Premium = `User.has_premium_access()` (`apps/users/models.py:322`).
- The day is the user's local day from `utc_offset_minutes`. The valid range is
  `-840..840`; an absent or invalid value means 0 (UTC).
- A scan counts only when its job ends `done` (charged as its mode) or
  `degraded` (charged as **identify**). Failed or cancelled jobs cost nothing.
  An active job reserves its slot.
- Scan photos are **never** saved through the default storage. In prod that
  storage serves public permanent URLs (`settings.py:549-581`).
- Push payload key is `"event"` (not `"type"`). Collapse key is per event type:
  `"scan-job-finished"`.
- Copy, verbatim:
  - "This scan is taking a little longer than usual." with buttons "Wait" and
    "Cancel".
  - Failed scan: "We couldn't check your plant" with the button "Try again".
  - Degraded result: "We named your plant but couldn't check its health. Your
    check wasn't used."
  - Push title "Your plant check is ready" (done or degraded) or "We couldn't
    check your plant" (failed).
  - Home: label "Plant health check"; headline "What's wrong with your " plus
    "plant?" in the accent colour; body "Photograph the problem. We'll name the
    plant, find the cause and tell you what to do."; primary button "Check a
    sick plant"; link "Just identify a plant".
  - Bottom bar: centre button tooltip "Check a plant".
  - Onboarding: "Check on your first plant".
- Old endpoints `identify/` and `disease-requests/` stay unchanged.
- No direct push to main: one branch and PR per phase, and
  `gh pr merge --auto --squash --delete-branch` after review.
- Backend: the full `python -m pytest` runs before the PR, because an
  app-scoped run is a false green. Mobile: `dart run build_runner build
  --delete-conflicting-outputs`, then `flutter analyze`, then the **full**
  `flutter test` before the PR push.
- Celery tasks follow `docs/rules/celery.md`:
  - retry config declared
  - idempotent claims
  - IDs, not objects
  - `SoftTimeLimitExceeded` re-raised first
  - test packages patch `.delay` to `.apply`
- **Owner step before Phase B merges:** create a private R2 bucket with no
  public domain, and set `R2_SCANS_BUCKET_NAME` on Railway. Then declare it in
  `.railway/railway.ts` with `preserve()`. With `USE_R2=True`, boot fails fast
  without it.

## Review Focus

1. **Two Done taps, or two devices, racing the last diagnosis.** Exactly one
   job is created; the other gets 429 `allowance_exhausted`. Test in Task B4.
2. **A worker dies mid-job, so the job sits in `processing` forever and holds
   the user's only diagnosis.** After `SCAN_JOB_STALE_MINUTES` (10) it is
   expired to `failed` and stops counting. Test in Task B3.
3. **Cancel lands while the task is finishing.** Cancelled wins: no charge, no
   push. Test in Task B3.
4. **A user requests another user's job or photo by UUID.** 404, and no
   existence leak. Test in Task B4.
5. **The app is killed after upload and relaunched after the job finished.**
   The tracker restores from secure storage, writes the collection entry once
   and shows the ready pill. Test in Task C2.

**Interfaces:**

- Consumes: B1's `identify_plant(..., images=, health_images=, quota_reserve=)` and B2's models.
- Produces:
  - `CombinedPlantIdentificationService.scan(self, shots: Mapping[str, bytes], mode: str) -> dict` returns the same keys as `identify_plant`.
    - PlantNet organ map: `leaf→"leaf"`, `whole→"habit"`, `flower→"flower"`. `problem` is sent to PlantNet only when it is the sole shot, as `"leaf"`.
    - **diagnose**:
      - Run in parallel on the existing executor.
      - Plant.id gets `images=` the non-problem shots, or `[problem]` if there are none; `health_images=[problem]`; `include_diseases=True`.
      - PlantNet gets the mapped shots.
    - **identify**:
      - PlantNet first.
      - If the top PlantNet probability is ≥ `SCAN_PLANTNET_CONFIDENCE_FLOOR`, build the results from PlantNet alone. Plant.id becomes `ProviderOutcome(None, "skipped", configured=False)`.
      - Otherwise call Plant.id with `include_diseases=False, quota_reserve=settings.PLANT_ID_DIAGNOSIS_RESERVE`.
      - If Plant.id fails, return PlantNet's result.
  - `classify_scan(mode: str, results: dict) -> tuple[str, str]` returns `(status, charged_as)`:
    - no `combined_suggestions` → `("failed", "")`
    - identify → `("done", "identify")`
    - diagnose with `disease_detection_status == "ok"` → `("done", "diagnose")`
    - otherwise → `("degraded", "identify")`
  - `summarize_scan_result(mode: str, results: dict) -> dict` gives the client shape:
    - `{"plant_name", "scientific_name", "confidence", "description", "suggestions": [{"plant_name","scientific_name","probability"}…≤5], "diagnosis": None | {"state": "found"|"healthy"|"unavailable", "name", "probability", "description"}}`
    - `diagnosis` is `None` for identify mode.
    - `"unavailable"` when `disease_detection_status != "ok"`.
    - `"healthy"` when `disease_detection` is None or reports healthy. Read the exact `is_healthy` shape from `plant_id_service._format_response` :443.
    - `"found"` otherwise.
  - `expire_stale_jobs(user_id: int) -> int` sets active jobs older than `SCAN_JOB_STALE_MINUTES` to `failed` with `failure_reason="stale"`, as one conditional `UPDATE`.
  - Celery `run_scan_job(self, job_id: int) -> None`:
    - Decorator: `@shared_task(bind=True, max_retries=1, acks_late=True, reject_on_worker_lost=True, soft_time_limit=150, time_limit=180, ignore_result=True)`.
    - Claim: `filter(pk=job_id, status__in=ACTIVE_STATUSES).update(status="processing", attempts=F("attempts")+1)`. A 0 return means stop, because the job was cancelled, finished or expired.
    - Read the photo bytes from storage and call `scan()`.
    - If the outcome is `failed` and `self.request.retries == 0`, then `raise self.retry(countdown=5)`. This is the one automatic retry.
    - Finalize with a conditional `UPDATE … WHERE status="processing"` that sets `status`, `charged_as`, `result=summarize_scan_result(...)`, `failure_reason` and `finished_at`. If that matches 0 rows (cancelled meanwhile), do nothing more.
    - On done or degraded, call `apps.users.onboarding.record_first_identification(user)`.
    - Then `transaction.on_commit(lambda: notify_scan_job_finished.delay(job_id))`.
    - Re-raise `SoftTimeLimitExceeded` before any generic `except`. On an unexpected exception, finalize as `failed` with `failure_reason="error"`.
  - Celery `notify_scan_job_finished(self, job_id: int) -> None`:
    - Dedup claim: `filter(pk=job_id, notified_at__isnull=True, status__in=("done","degraded","failed")).update(notified_at=now())`.
    - Then use `device_tokens_for_users([user_id])` and enqueue `send_scan_push_to_device(owner_id, token, data, content)` per token.
    - `data = {"event": "scan_job_finished", "job_id": str(uuid), "status": status}`.
  - Celery `send_scan_push_to_device(self, owner_id: int, token: str, data: dict, content: list[str]) -> None` mirrors `garden_calendar/tasks.py:535-588` exactly:
    - `is_firebase_available` / `get_fcm_client` early returns
    - `is_registered` re-check
    - `send_fcm_message(fcm, token, data, tuple(content), "scan-job-finished")`
    - credentials, dead-token and transient-retry handling

**Files:**

**Interfaces:**

- Produces:

  - `class ScanTrackerState { final TrackerPhase phase; final double? uploadProgress; final ScanJob? job; final CaptureResult? lastCapture; }`
  - `@Riverpod(keepAlive: true) class ScanJobTracker`:
    - `Future<void> submit(CaptureResult r)`:
      - Pre-check `allowance()`. If `remainingFor(mode) == 0` or (diagnose and `!plantIdAvailable`), throw `ScanRefused` locally **before** upload.
      - Otherwise set `uploading` and upload.
      - Write the job id to secure storage key `scan_job.pending_id`, then set `waiting`.
      - A 409 `ScanRefused(code: 'scan_in_progress', jobId:)` is **adopted**, not rethrown: store that id, GET the job, and move to `waiting` (this recovers a job whose upload response was lost to a kill). Rethrow other `ScanRefused` / `ApiException`.
    - `Future<void> cancel()` calls the API cancel, clears the stored id and sets `idle`.
    - `Future<void> retry()` re-submits `lastCapture`. It is only valid in `failed`.
    - `void dismiss()` clears the stored id and sets `idle`.
    - `Future<void> restore()` is called once from `build` via `unawaited`. If a stored id exists, it GETs the job and applies it.
    - `Future<void> onPush(String jobId)` re-GETs the job if it matches.
  - Behaviour:
    - Polling: in `waiting` or `slow`, a `Timer.periodic(Duration(seconds: 3))` GETs the job, with `ref.onDispose` cancel and an app-paused stop/start via `AppLifecycleListener`.
    - `slow` is set when `slowAfterSeconds` (from the allowance; default 45) have passed since the upload finished.
    - On `hasResult`: `ready`, and save to the collection **once**, using `Plant(id: job.id, name, scientificName, description, care: [], imageUrl: job.coverPhoto, timestamp)`. The Firestore doc id = job id, so a repeat is idempotent.
    - On `failed`: `failed`, keeping `lastCapture`.
    - On `cancelled`: `idle`.
    - The stored id is cleared on `ready`/`failed`/`cancelled` handling, after the save.
    - The secure storage is injected as `scanTrackerStorageProvider = Provider<FlutterSecureStorage>` so tests can fake it (pattern `LiveToastFlags`, `lib/features/forum/live/live_updates_settings.dart`).
    - The clock is injected the same way (`scanTrackerClockProvider = Provider<DateTime Function()>`).
